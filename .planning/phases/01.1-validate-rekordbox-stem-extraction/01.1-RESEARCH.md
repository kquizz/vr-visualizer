# Phase 1.1: Validate Rekordbox Stem Extraction - Research

**Researched:** 2026-04-16
**Domain:** Rekordbox stem separation internals, macOS audio routing, stem extraction feasibility
**Confidence:** HIGH

## Summary

The primary investigation question -- "Can Rekordbox's 4 stem outputs be individually captured as separate audio streams?" -- has a clear answer: **Rekordbox does NOT cache stem audio to disk, and provides only a single mixed master output**. Stems are processed in real-time by an AI model running on the CPU during playback. The analysis results are not saved; reloading a track requires re-analysis. The `.3EX` files found in the ANLZ directory contain ML model embeddings (msgpack-encoded floating point data), not audio.

This means the stem cache investigation path described in CONTEXT.md will quickly hit a dead end, which is itself a valuable finding. The spike should confirm this definitively, then evaluate the two remaining approaches: (1) solo-and-capture via BlackHole (play the track 4 times, soloing one stem each time, recording through BlackHole), and (2) Demucs pre-separation as the known-working baseline.

**Primary recommendation:** Structure the spike as: quick cache hunt (confirm dead end) -> BlackHole install + solo-and-capture test -> compare Rekordbox stem quality vs Demucs -> document findings for Phase 3 architecture.

### Rekordbox Data Directory Map (macOS)
```
~/Library/Pioneer/rekordbox/
├── master.db                          # Encrypted SQLite (SQLCipher) - track metadata
├── master.backup.db                   # Backup of above
├── share/PIONEER/USBANLZ/             # Analysis files per track
│   └── {hash}/{uuid}/
│       ├── ANLZ0000.DAT               # Waveforms, beat grids, cue points
│       ├── ANLZ0000.EXT               # Extended waveforms, song structure
│       ├── ANLZ0000.2EX               # Color waveforms for newer players
│       └── ANLZ0000.3EX               # ML embeddings (NOT audio stems)
├── share/PIONEER/Artwork/             # Album art cache
├── ExtData.edb                        # Extended data (encrypted)
└── datafile.edb                       # Data file (encrypted)

~/Music/rekordbox/
├── Recording/                         # DJ set recordings
└── Sampler/                           # Sample packs (Groove Circuit, Merge FX, etc.)
    └── Capture/                       # Empty - stems NOT stored here
```

### Solo-and-Capture Workflow
```
For each stem (vocals, drums, bass, inst):
  1. Load track in Rekordbox Performance mode
  2. Wait for stem analysis to complete (CPU-intensive)
  3. Solo the target stem (STEM ISO mode or ACTIVE STEM mute others)
  4. Start recording from BlackHole input (ffmpeg or Audacity)
  5. Play the track
  6. Stop recording
  7. Save as WAV
Result: 4 WAV files, one per stem
```

### Anti-Patterns to Avoid
- **Spending too long on cache investigation:** Research strongly indicates stems are NOT cached as audio. Cap the cache hunt at 30 minutes.
- **Trying to capture all 4 stems simultaneously:** Rekordbox has one master output. Even with BlackHole 16ch, Rekordbox doesn't route stems to separate channels. Must solo one at a time.
- **Forgetting to disable system sounds:** BlackHole captures ALL audio routed to it. Mute notifications/system sounds before recording.

## Common Pitfalls

### Pitfall 1: Rekordbox Stem Cache Rabbit Hole
**What goes wrong:** Spending hours searching for stem audio files that don't exist on disk.
**Why it happens:** The CONTEXT.md correctly identified this as the "highest-value investigation" based on reasonable assumptions. However, research confirms Rekordbox processes stems in real-time without caching audio.
**How to avoid:** Cap the cache investigation at 30 minutes. Confirm the .3EX files are ML embeddings (not audio) and move on.
**Warning signs:** Finding only binary data with msgpack/embedding headers, no WAV/FLAC/MP3 files in Rekordbox directories.

### Pitfall 2: BlackHole Audio Feedback Loop
**What goes wrong:** Creating a feedback loop where BlackHole output feeds back into BlackHole input, causing audio echo or screeching.
**Why it happens:** Incorrect Multi-Output Device configuration in Audio MIDI Setup.
**How to avoid:** Set up the Multi-Output Device carefully: Rekordbox outputs to BlackHole, recording app reads from BlackHole. Monitor via separate physical output (headphones).
**Warning signs:** Echo, delay, or screeching when playback starts.

### Pitfall 3: Rekordbox CPU Overload During Stem Analysis
**What goes wrong:** Rekordbox stutters or drops audio quality during real-time stem separation, corrupting the recording.
**Why it happens:** Stem separation runs an AI model on CPU in real-time. Combined with recording overhead, this can overwhelm the system.
**How to avoid:** Close unnecessary applications. Check Rekordbox Preferences > Extensions > STEMS > Multi-thread setting. Use "Prioritize sound quality" if CPU allows it.
**Warning signs:** Audio crackling, gaps in recorded stems, Rekordbox latency warnings.

### Pitfall 4: Recording Captures System Audio
**What goes wrong:** The recorded stem includes macOS notification sounds, other app audio, etc.
**Why it happens:** BlackHole captures everything routed to it as output device.
**How to avoid:** Set Rekordbox's output specifically. Mute all notifications. Close other audio-producing apps. Or: use Rekordbox's "PC MASTER OUT" option which routes only Rekordbox audio.
**Warning signs:** Random pings or sounds in the recorded stem.

### Pitfall 5: Stem Quality Setting Not Configured
**What goes wrong:** Stems sound muddy or have obvious artifacts because Rekordbox is in low-quality mode.
**Why it happens:** Rekordbox defaults to a performance-friendly stem quality that may not be maximum.
**How to avoid:** Check Preferences > Extensions > STEMS tab. Set to "Prioritize sound quality" for validation purposes.
**Warning signs:** Stems sound noticeably worse than Demucs output.

## Code Examples

### Recording Audio from BlackHole via ffmpeg
```bash
# List available audio devices on macOS
ffmpeg -f avfoundation -list_devices true -i ""

# Record from BlackHole 16ch to WAV (stop with Ctrl+C)
ffmpeg -f avfoundation -i ":BlackHole 16ch" -acodec pcm_s16le -ar 44100 output_stem.wav

# Record for a specific duration (e.g., 240 seconds for a 4-min track)
ffmpeg -f avfoundation -i ":BlackHole 16ch" -acodec pcm_s16le -ar 44100 -t 240 drums_stem.wav
```

### Audio Quality Comparison with sox
```bash
# Get audio statistics
sox stem_file.wav -n stats

# Generate spectrogram for visual comparison
sox stem_file.wav -n spectrogram -o stem_spectrogram.png

# Compare two stems (Rekordbox vs Demucs)
sox rekordbox_drums.wav -n spectrogram -o rb_drums_spec.png
sox demucs_drums.wav -n spectrogram -o demucs_drums_spec.png
```

### Inspecting .3EX Files (Confirming Not Audio)
```bash
# Check file header -- audio files start with RIFF (WAV), fLaC, ID3, etc.
xxd ANLZ0000.3EX | head -5
# If you see "embedding" in msgpack format, it's ML data, not audio

# Check with file command
file ANLZ0000.3EX
```

### Demucs Baseline (Already Working)
```bash
# Separate track into 4 stems (drums, bass, vocals, other)
demucs -n htdemucs "path/to/track.mp3"
# Output: ./separated/htdemucs/track/{drums,bass,vocals,other}.wav

# Higher quality (4x slower)
demucs -n htdemucs_ft "path/to/track.mp3"
```

## Key Research Findings

### Finding 1: Rekordbox Does NOT Cache Stem Audio (HIGH confidence)
- Stems are processed in real-time by an AI model on the CPU during playback
- Analysis results are not saved -- reloading a track requires re-analysis
- The `.3EX` files in `USBANLZ/` contain ML embeddings (msgpack-encoded float data), not audio
- The `Sampler/Capture` directory is empty and unrelated to stems
- ANLZ file format (documented by pyrekordbox and Deep Symmetry) has no stem audio sections
- **Sources:** Rekordbox FAQ, DJ.Studio stem comparison article, pyrekordbox ANLZ format docs, direct inspection of local .3EX file

### Finding 2: Solo-and-Capture via BlackHole Is Viable (MEDIUM confidence)
- Rekordbox has STEM ISO and ACTIVE STEM modes for soloing individual stems
- BlackHole can capture Rekordbox master output on macOS
- Process: solo one stem, record through BlackHole, repeat 4 times
- Limitation: requires playing the track 4 times (once per stem)
- Confirmed working: BlackHole + Rekordbox routing documented for OBS streaming
- **Sources:** BlackHole GitHub, Rekordbox FAQ on stems, Nick Brogna's Rekordbox+BlackHole guide

### Finding 3: Demucs Is Already the Proven Baseline (HIGH confidence)
- Already installed and producing 4-stem WAV output for this project
- Test stems exist at `audio/stems/test_*.wav` and `audio/separated/htdemucs/`
- HTDemucs v4 is current state-of-the-art for offline stem separation
- Apple Silicon MPS acceleration available (~5x speedup)
- **Sources:** Direct observation of project files, Demucs GitHub

### Finding 4: .3EX is a New Undocumented ANLZ Extension (LOW confidence)
- Found `.3EX` files in USBANLZ directories alongside `.DAT`, `.EXT`, `.2EX`
- Not documented by pyrekordbox or Deep Symmetry (they only document DAT/EXT/2EX)
- Header contains msgpack-encoded data with key "embedding" and float arrays
- Likely stores ML model embeddings used for stem separation inference
- ~5.5KB per track -- far too small to contain audio data
- **Sources:** Direct file inspection, absence from pyrekordbox docs
